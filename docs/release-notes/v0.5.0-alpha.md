# Kinfold v0.5.0-alpha

Availability and platform release: a standby controller that keeps devices
working when the primary fails, and a macOS client. Builds on v0.4.0-alpha;
not independently audited — use it for evaluation and non-critical networks.

## Upgrade notes

- **Update the controller and all clients together.** The signed
  configuration now lists the controller addresses and the state can hold
  standby controllers; v0.4 binaries reject both because of strict decoding.
- Clients keep a small `<credential>.controllers` file next to the
  credential (the controllers they may fail over to). It must stay writable;
  without it a client falls back to the server in its credential after a
  restart.
- Devices now try the other controllers when one answers 503; with a single
  controller nothing changes.

## New

- **Standby controller (#26).** `replica-add` on the primary creates a
  credential for a standby host; `serve -standby` replicates the complete
  state every two seconds and serves signed configuration and the relay
  under its own certificate. Devices learn all controller addresses from
  their signed configuration, fail over on network errors and return to the
  primary when it is back. Promotion after losing the primary is a manual
  `replica-promote` followed by a restart without `-standby`; there is no
  quorum (#63). A standby that cannot replicate serves its last state for at
  most `-standby-max-age` (default one hour).
- **macOS client (#24).** `kinfold run` works on macOS (amd64 and arm64)
  through a utun interface, with the same certificate checks, packet
  filtering, direct path and renewal as on Linux. It needs root; the kernel
  chooses the interface name. Windows and mobile clients remain open (#64).

## Quality assurance

An independent review of all changes before the release found one high,
three medium and three low issues, all fixed (see
`docs/review-v0.1-copilot.md`): the documented standby promotion did not
work (now `replica-promote`), a standby with broken replication served its
last state without limit (now at most `-standby-max-age`), and devices did
not fail over when the primary answered without a valid state. A second
review of these fixes found three smaller issues, also fixed. Race
tests, five fuzz targets, the Docker integration test (14 scenarios) and a
manual macOS end-to-end test over IPv4 (macOS client ↔ Linux client through
the tunnel, `scripts/macos-smoke.sh`) pass; IPv6 on macOS is not yet tested
end to end.

## Security model changes

A standby holds the complete controller state including the CA key and the
configuration signing key, so it must be protected like the primary. Two
controllers serving as primary at the same time give devices diverging
configurations. A revocation made while a standby cannot reach the primary
takes up to `-standby-max-age` to reach devices served by that standby. See `docs/SECURITY-MODEL.md`, `docs/OPERATIONS.md` and
decisions D-028 to D-032.
