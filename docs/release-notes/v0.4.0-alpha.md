# Kinfold v0.4.0-alpha

Trust and transport release: signed configuration with leases, and a direct
TCP path between devices that can reach each other. Builds on v0.3.0-alpha;
not independently audited — use it for evaluation and non-critical networks.

## Upgrade notes

- **Update the controller and all clients together.** `/config` now returns
  a signed envelope; v0.3 clients cannot use a v0.4 controller and vice
  versa.
- On its first start, a v0.4 controller adds a configuration signing key to
  its state (`config_key`). v0.3 binaries cannot read the state afterwards.
- Existing device credentials keep working: on the first `run` the client
  fetches the controller's signing key over the authenticated connection and
  stores it in the credential (when the file can be replaced; otherwise for
  that run only). New credentials carry it from the start.
- Clients keep a small `<credential>.seen` file next to the credential (the
  newest configuration they accepted). It must stay writable; deleting it
  only weakens rollback protection across one restart.
- A client now closes its tunnel immediately when the controller refuses its
  configuration request (device removed, invalid controller state), instead
  of after the 30-second grace period. A controller that is shutting down
  does not count as a refusal.
- Peer IDs must now be unique ignoring case; a state with IDs such as
  `alice` and `Alice` no longer loads.
- If the controller's clock is set back between restarts, devices reject its
  configuration until the clock catches up; `kinfold seen-reset` resets a
  device (see the operator guide). Device clocks may be up to five minutes
  off.

## New

- **Signed configuration with leases (#22).** Every configuration a device
  receives is signed with a dedicated controller key (separate from the CA
  key), names the device, and carries an issue time and a two-minute lease.
  Devices verify it, refuse older configurations than they already accepted
  (also across restarts) and close the tunnel when the lease runs out.
- **Direct connections (#21).** `run -direct-listen :51900` lets a device
  accept direct mutual-TLS sessions; peers learn its addresses from their
  signed configuration and connect directly, falling back to the relay when
  that is not possible. Relayed sessions switch to the direct path when it
  becomes available. Same certificate checks and packet filtering as before;
  no NAT hole punching yet (#62).

## Quality assurance

An independent review of all changes before the release found three medium
and seven low issues, all fixed (see `docs/review-v0.1-copilot.md`), among
them the start-up fetch ignoring the rollback watermark, case-folded peer
IDs, the clock dependence of leases and an explicit acceptance step for
direct sessions. Race tests, five fuzz targets and the Docker integration
test (14 scenarios, including the direct path) pass.

## Security model changes

Traffic no longer always passes the relay, so revocation is now enforced by
the devices themselves: a configuration change ends affected sessions on
both ends within one poll interval, an explicit refusal by the controller
closes the tunnel at once, and an unreachable controller ends everything
after 30 seconds or at lease expiry. See `docs/SECURITY-MODEL.md` and
decisions D-025 to D-027.

```sh
git checkout v0.4.0-alpha

```
