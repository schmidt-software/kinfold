# Kinfold v0.1-copilot — User Guide

[Deutsche Fassung](../de/v0.1-copilot.md) · Tag date: 2026-11-07 · Status: experimental alpha prototype, not independently audited. Do not use it in production or to protect confidential data.

---

## 1. About this version

### What Kinfold is

Kinfold is a self-hosted overlay network for IPv4 and, optionally, IPv6. You run one **controller** on a server you control. The controller holds a private certificate authority (CA), the list of member devices with their fixed overlay addresses, and the directional rules that say which device may send traffic to which other device. The same process also acts as a **relay**: devices connect to it over TCP, and it pairs two devices and forwards an end-to-end encrypted stream between them. Each device runs a small client that creates a virtual network interface (a TUN device) and carries IP packets to the other members through the relay.

Kinfold uses its own protocol. It is not compatible with any other network or tunnelling product, does not register with any external service and needs no third-party account.

### This version: the prototype baseline

`v0.1-copilot` is the first tagged state of the project. It is the prototype baseline that was developed autonomously before the first structured review. At this tag the project had not yet been renamed to Kinfold:

- the binary is called **`my-zerotier`** (the module name is `my-zerotier`),
- the README, the decision record (`ENTSCHEIDUNGEN.md`) and the security model (`SICHERHEITSMODELL.md`) at this tag are written in German,
- the default TUN interface name is `mzt0`, and the integration script uses the environment variable `MYZT_TEST_IMAGE`.

This guide uses the commands exactly as they exist at this tag, so every example calls `my-zerotier`. Later versions use a different binary name and many different commands; do not mix this guide with guides for later tags.

### What is new compared with the previous tag

There is no previous tag. `v0.1-copilot` is the starting point of the version history, and there are no release notes for it. Everything described in this guide is "new" in the sense that it is the initial feature set:

- one private IPv4 network and an optional IPv6 ULA `/64` with up to 32 explicitly authorized devices,
- a self-hosted controller and TCP relay with mutual TLS 1.3,
- an additional end-to-end mutual TLS 1.3 session between every pair of devices that talk to each other,
- directional allow rules with default deny for new networks,
- experimental service rules (protocol and destination port),
- two enrollment methods: `add-peer` (controller generates the key) and the offline `keygen` / `approve` / `enroll` flow (device generates the key),
- offline device key rotation (`rotate-peer`) and server certificate renewal (`renew-server`),
- a Linux TUN client with automatic reconnection,
- a Docker-based end-to-end demonstration script.

### Who this guide is for

This guide is for administrators who want to set up and run a small private network of Linux machines and who are comfortable with a shell, file permissions, TLS certificates and basic IP networking, but who are new to this project. It explains each task step by step and points out where a step matters for security.

### The example network used throughout

| --- | --- |

## 2. Concepts

### Controller

The controller is the single source of truth. Its whole state lives in one file, `state.json`, inside the data directory (by default `controller-data`). That file contains:

- the controller address that devices use (`server`, for example `vpn.example.com:8443`),
- the CA certificate and the **CA private key**,
- the controller's own TLS server certificate and key,
- the network configuration: the IPv4 network, the optional IPv6 network, the list of devices (ID, IPv4, optional IPv6, certificate) and the policy,
- a history of public-key fingerprints that were ever authorized (`used_peer_keys`).

All administrative commands (`add-peer`, `allow`, `remove-peer`, ...) are offline commands: they edit `state.json` directly on the controller host. There is no administrative network API. The running controller (`serve`) notices changes to the file by itself.

Because the controller owns the CA key and decides who is a member, it is a **full trust anchor**. Anyone who can read or modify `controller-data` can issue identities or replace the configuration.

### Relay

The relay is part of the controller process. A device opens a TLS connection to the controller, authenticates with its device certificate and sends a `CONNECT /relay?peer=<id>` request. When the other device asks for the reverse direction, the relay connects the two raw streams. The relay does not decrypt the traffic between the devices; it only sees metadata such as which devices talk to each other, when, and how much data flows.

There are no direct connections between devices in this version. All device-to-device traffic goes through the relay over TCP.

### Devices (peers)

A device (called "peer" in the CLI) is a Linux machine that runs `my-zerotier run`. Each device has:

- an **ID**: 1 to 32 characters, starting with a letter or digit, followed by letters, digits, `_` or `-` (for example `alice`),
- a fixed **IPv4 address** inside the overlay network (for example `10.77.0.1`),
- optionally a fixed **IPv6 address** inside the IPv6 ULA network,
- an Ed25519 key pair and a certificate signed by the controller's CA.

At most 32 devices are supported per network.

### CA and certificates

`init` creates:

- a self-signed CA (common name `my-zerotier CA`), valid for **10 years**,
- a controller server certificate for the host part of the controller address, valid for **1 year** (never longer than the CA).

Device certificates are also valid for at most **1 year** and never longer than the CA. All keys are Ed25519. There is no CA rotation in this version.

A certificate alone never grants access. The controller identifies a device by the SHA-256 fingerprint of its certificate and looks it up in the currently loaded device list. A certificate that was signed by the CA but is no longer in the list is rejected.

### Credential file

A device needs one JSON file, the **credential**, to run. It contains four fields:

| Field | Content |
| --- | --- |
| `server` | Controller address, for example `vpn.example.com:8443` |
| `ca` | The controller CA certificate (PEM) |
| `cert` | The device certificate (PEM) |
| `key` | The device **private key** (PEM) |

The credential is secret: whoever has it can impersonate the device. New credential files are created with mode `0600` and are never overwritten (a command fails if the output file already exists).

### Directional rules and default deny

New networks start with **default deny**: no device may send anything to any other device. You grant access per direction:

- `allow -from alice -to bob` permits packets from alice to bob,
- replies from bob to alice need a second rule, `allow -from bob -to alice`.

Both ends check the rules independently. The sender only forwards permitted packets and the receiver only accepts permitted packets. The relay additionally refuses to pair two devices if neither direction is allowed.

Optionally, you can add an experimental **service filter** on top: with it enabled, only listed protocols and destination ports are allowed in each direction (see section 9).

Networks created by older, unversioned prototype states may have no policy at all ("legacy" networks); they allow all traffic until you run `policy-enable`. Every network created with `init` at this tag already has default deny.

### Configuration reload

- The running controller re-reads `state.json` about **once per second**. If the configuration changed, it drops all relay sessions so that devices reconnect under the new rules. If the file is invalid or unreadable, the controller closes all sessions and answers every request with an error until the file is valid again ("fail closed").
- Each running device asks the controller for the configuration about **every 2 seconds**. On a change it tears down its TUN interface and recreates it with the new configuration. If a request fails, the device closes its tunnel and keeps retrying.
- The CLI only confirms that the file was written. It does not confirm that the controller or any device has applied the change.

Changes to the CA or the controller's server certificate are not reloaded; they require a controller restart.

### Configuration revision

When a policy is present, a device must send the hash (revision) of the configuration it is using when it asks the relay for a session. The relay rejects devices with an outdated configuration. This ensures that up-to-date clients use the current rules. It is **not** a proof that the client software is unmodified: a tampered client can compute the same hash.

### Features that do not exist at this tag

This version has no signed configuration, no direct device-to-device path, no standby controller, no enrollment tokens, no online certificate renewal and no metrics. See section 11.4.

## 3. Requirements

### Controller

| Requirement | Details |
| --- | --- |
| Operating system | Linux or macOS. The administrative commands that change state use an advisory file lock that exists only on Linux and macOS; on other systems they fail with `controller state locking is supported only on Linux and macOS`. |
| Privileges | An ordinary, dedicated user account is enough. No root is needed unless you listen on a port below 1024. |
| Network | One inbound TCP port reachable by all devices (default `:8443`). |
| DNS or IP | A stable DNS name or IP address that every device uses. It is written into the server certificate at `init` and cannot be changed later without a new setup. |
| File system | One with working `fsync` and `flock`; a local disk is recommended. |

### Devices

| Requirement | Details |
| --- | --- |
| Operating system | **Linux only.** On other systems `run` fails with `TUN client is currently supported only on Linux`. |
| Kernel interface | `/dev/net/tun` must exist. |
| Tools | The `ip` command (iproute2 or BusyBox) in `PATH`. The client calls it to assign addresses and bring the interface up. |
| Privileges | root or `CAP_NET_ADMIN` for `run`. `status` needs no special privileges. |
| Network | Outbound TCP to the controller address. No inbound ports are needed. |
| Addressing | The overlay networks (`10.77.0.0/24`, `fd77::/64`) must not overlap with any local network or route on the device. |

### Build requirements

- Go **1.24** or newer (`go.mod` at this tag declares `go 1.24`).
- No external Go modules are needed; the project uses only the standard library.
- For the Docker demonstration: Docker with Linux containers, the ability to grant `NET_ADMIN` and `/dev/net/tun` to containers.

### Ports summary

| Direction | Protocol | Port | Purpose |
| --- | --- | --- | --- |
| Device to controller | TCP | 8443 (or what you chose) | Configuration requests and relayed sessions |

There is no UDP traffic in this version.

## 4. Installation

### No release binaries

`v0.1-copilot` has **no GitHub release, no release notes file and no release script**. You must build the binary from source. There are therefore no published checksums to verify; instead, make sure you build from the tagged commit of a repository you trust.

### Build from source

1. Get the source and check out the tag:

   ```sh
   git clone <repository-url> kinfold
   cd kinfold
   git checkout v0.1-copilot
   ```

2. Build the binary for the machine you are on (typically the controller):

   ```sh
   go build -o my-zerotier .
   ```

3. Check that it runs. Without arguments (or with `-h`) it prints the command list:

   ```sh
   ./my-zerotier -h
   ```

   Every command prints its options with `-h`, for example `./my-zerotier serve -h`.

### Cross-compiling for Linux devices

Go cross-compiles without extra tools. Build one binary per device architecture:

```sh
# Linux on x86-64
GOOS=linux GOARCH=amd64 go build -o my-zerotier-linux .

# Linux on ARM64 (for example a Raspberry Pi 4 or 5 with a 64-bit OS)
GOOS=linux GOARCH=arm64 go build -o my-zerotier-linux-arm64 .
```

Copy the matching binary to each device over a trusted channel, for example:

```sh
scp my-zerotier-linux alice.example.net:
```

The same binary contains all commands. On devices you will mainly use `run`, `status`, `keygen` and `enroll`.

### Running the tests (optional)

```sh
go test -race ./...
go vet ./...
```

## 5. Quick start: the Docker demonstration

The repository contains an end-to-end script that sets up a complete network in Docker. It is the fastest way to see the system work before you touch real machines.

### Prerequisites

- Go 1.24 or newer,
- Docker with Linux containers,
- permission to start containers with `NET_ADMIN` and `/dev/net/tun`,
- the image `alpine/socat:latest` (downloaded automatically if missing). You can choose another image that provides a shell, `ip`, `ping`, `ping6`, `nc` and `socat` with the environment variable `MYZT_TEST_IMAGE`.

### Run it

```sh
sh scripts/integration-docker.sh
```

Or with a different image:

```sh
MYZT_TEST_IMAGE=my-test-image:latest sh scripts/integration-docker.sh
```

### What it does

The script:

1. builds a host binary and a Linux binary for the Docker architecture (amd64 or arm64),
2. creates a temporary controller state with `init -server controller:8443`,
3. enrolls `alice` with the offline flow (`keygen`, `approve`, `export-ca`, `enroll`) and `bob` and `charlie` with `add-peer`,
4. allows `alice -> bob` and `bob -> alice` (charlie gets no rule),
5. creates an isolated Docker network and starts one controller and three client containers,
6. checks, printing `... : OK` for each step:
   - bidirectional ICMP between alice and bob,
   - that charlie is blocked by default deny,
   - a TCP transfer through the tunnel,
   - IPv6 ICMP, default deny and TCP over IPv6,
   - reconnection after a controller restart,
   - that a broken `state.json` makes the controller fail closed and that it recovers,
   - server certificate renewal followed by a restart,
   - that a policy change ends active sessions,
   - offline key rotation of a device,
   - the experimental service filter,
   - revocation of a device without restarting controller or clients,
   - a clean TUN shutdown.

It removes its own containers, its network and its temporary files when it exits and does not modify any other containers. All keys it creates are temporary.

## 6. Setting up the controller

### 6.1 Choose the controller address

Decide on the address that every device will use, for example `vpn.example.com:8443`. The host part (`vpn.example.com`) becomes the name in the controller's TLS certificate; devices verify it on every connection. If you use an IP address instead of a name, the certificate contains that IP address.

Choose carefully: at this tag there is no command to change the controller address later. Moving to a different name means a new setup and new credentials for every device.

The port in the address is the port devices connect to. It does not have to be the same as the port the controller listens on (`serve -listen`), for example if a firewall forwards port 8443 to another local port.

### 6.2 Initialize the state

Run as the user that will own the controller:

```sh
./my-zerotier init -data controller-data \
  -server vpn.example.com:8443 -network 10.77.0.0/24
```

Expected output:

```text
Created controller state in controller-data. Keep it secret and back it up.
```

`init` options:

| Flag | Default | Meaning |
| --- | --- | --- |
| `-data` | `controller-data` | New data directory. It must not exist yet; `init` creates it with mode `0700`. |
| `-server` | (required) | Public `host:port` that devices use to reach the controller. |
| `-network` | `10.77.0.0/24` | IPv4 overlay network. Must be a canonical prefix (host bits zero), `/30` or larger. |

The new network already has a default-deny policy with no rules.

### 6.3 File locations and permissions

| Path | Content | Protection |
| --- | --- | --- |
| `controller-data/` | Data directory | Mode `0700`, created by `init` |
| `controller-data/state.json` | Complete controller state including the **CA private key** | Mode `0600`; replaced atomically on every change |
| `controller-data/.state.lock` | Lock file for concurrent CLI writers | Do not delete while the controller is in use |
| `credentials/` (your choice) | Credential files created by `add-peer` | Create with `mkdir -m 700 credentials` |

Why this matters: whoever can read `state.json` can sign new device certificates and therefore join the network as any device. Keep the directory owned by a dedicated account, never put it in version control (the default paths `controller-data/` and `credentials/` are listed in the tag's `.gitignore`, other paths are not), and back it up only in encrypted form.

At this tag the controller does not itself check the permissions of `state.json` when loading it; it is your job to keep them tight.

### 6.4 Start the controller

```sh
./my-zerotier serve -data controller-data -listen :8443
```

Expected output:

```text
Controller listening on [::]:8443
```

`serve` options:

| Flag | Default | Meaning |
| --- | --- | --- |
| `-data` | `controller-data` | Data directory to serve. |
| `-listen` | `:8443` | TCP listen address, for example `:8443` (all interfaces) or `192.0.2.10:8443`. |

What `serve` does:

- loads and fully validates `state.json` (configuration, key history, CA and server key pairs, server certificate including host name and validity, CA signature of every device certificate) and refuses to start if anything is wrong,
- prints `WARNING: legacy network allows all peer traffic; use policy-enable to opt into default-deny.` if the network has no policy,
- accepts only TLS 1.3 with a client certificate signed by the CA,
- accepts at most 1,152 simultaneous TCP connections (including TLS handshakes),
- re-reads `state.json` every second (see section 2),
- on `Ctrl-C` or `SIGTERM` closes all relay sessions immediately and waits up to five seconds for running HTTP requests.

Open the listen port in the host firewall for the devices. Nothing else needs to be reachable.

### 6.5 Running the controller as a service

This version ships **no service units** and no packages. If you want the controller to start at boot and restart after a failure, run `my-zerotier serve` under your system's service manager yourself, as a dedicated unprivileged user whose home or working directory contains `controller-data`. Keep in mind:

- the process must be restarted after `renew-server`,
- it reacts to `SIGTERM` with a clean shutdown,
- it writes its log to standard output and standard error.

## 7. Adding devices

There are two ways to authorize a device. Both end with the same result: an entry in `state.json` and a credential file on the device.

| Method | Where the private key is created | Steps | When to use |
| --- | --- | --- | --- |
| `add-peer` | On the controller | 1 command, then transfer the credential | Quick setup, labs, devices you fully control |
| Offline enrollment: `keygen` / `approve` / `enroll` | On the device | 3 steps with fingerprint checks | Preferred when the private key should never leave the device |

There are no enrollment tokens or online join commands in this version.

### 7.1 Method A: `add-peer` (controller creates the key)

1. On the controller, create a private directory for credentials (once):

   ```sh
   mkdir -m 700 credentials
   ```

2. Authorize the devices:

   ```sh
   ./my-zerotier add-peer -data controller-data \
     -id alice -ip 10.77.0.1 -out credentials/alice.json
   ./my-zerotier add-peer -data controller-data \
     -id bob -ip 10.77.0.2 -out credentials/bob.json
   ```

   Output:

   ```text
   Authorized alice. Transfer credentials/alice.json securely; updated clients reload asynchronously.
   ```

   `add-peer` options:

   | Flag | Default | Meaning |
   | --- | --- | --- |
   | `-data` | `controller-data` | Controller data directory |
   | `-id` | (required) | Unique device ID |
   | `-ip` | (required) | IPv4 address inside the network; not the network or broadcast address; unique |
   | `-out` | (required) | New credential file; must not exist yet |

3. Transfer **only the matching** credential file to each device over a trusted, encrypted channel, for example:

   ```sh
   scp credentials/alice.json alice.example.net:
   ```

   On the device, keep the file private:

   ```sh
   chmod 600 alice.json
   ```

4. Delete the copy on the controller once the device has it, or keep it only in encrypted storage. The controller does not need it.

Why method B exists: with `add-peer`, the controller generates the device's private key and therefore sees it. If the controller host or the transfer channel is compromised, the device identity is compromised too.

Note on failure: `add-peer` writes the credential file first and then updates `state.json`. The two writes are not one transaction. If the second step fails, a credential file may exist without a matching entry. Check `state.json` (or `status` from a device) before you retry, and do not assume that a file means the device is authorized.

### 7.2 Method B: offline enrollment (device creates the key)

In this flow the private key is created on the device and never leaves it. The device sends a signed certificate request; the request proves that the sender holds the key, but it does **not** prove who the sender is. That is why you compare fingerprints over a separate, trusted channel (phone call, in person, a messenger you trust).

Requests, keys and certificate files are limited to 64 KiB each.

**Step 1 — on the device (alice): create key and request**

```sh
./my-zerotier-linux keygen -id alice -key alice.key -request alice.csr
shasum -a 256 alice.csr
```

`sha256sum alice.csr` gives the same value on systems without `shasum`.

| Flag | Meaning |
| --- | --- |
| `-id` | Device ID; must match the ID the administrator will approve |
| `-key` | New private key file (mode `0600`, never overwritten) |
| `-request` | New request file; must differ from `-key` |

Output:

```text
Created local private key alice.key and enrollment request alice.csr. Never transfer the private key.
```

Send **only** `alice.csr` to the administrator. Tell the administrator the SHA-256 value through an independent channel. **Never transfer `alice.key`.**

**Step 2 — on the controller: verify and approve**

```sh
shasum -a 256 alice.csr
./my-zerotier approve -data controller-data -id alice \
  -ip 10.77.0.1 -request alice.csr -out alice.crt
./my-zerotier export-ca -data controller-data -out ca.crt
openssl x509 -in ca.crt -noout -fingerprint -sha256
```

Compare the request hash with the value the device owner told you before running `approve`. Only approve requests whose origin you have confirmed.

`approve` options:

| Flag | Default | Meaning |
| --- | --- | --- |
| `-data` | `controller-data` | Controller data directory |
| `-id` | (required) | Approved device ID; must equal the ID inside the request |
| `-ip` | (required) | IPv4 address for the device |
| `-request` | (required) | The request file |
| `-out` | (required) | New certificate file |

`export-ca` writes the public CA certificate (`-out`, required). It prints `Exported CA. Verify its fingerprint through an independent trusted channel.`

Send `alice.crt` and `ca.crt` back to the device. These files are not secret. Tell the device owner the CA fingerprint through an independent, trusted channel.

What `approve` checks: the request must be a single PEM block, carry a valid signature, use an Ed25519 key, and name the same ID as `-id`. The public key must never have been authorized before (see key history in section 10.4). Extensions in the request are ignored; only the administrator's `-id` and `-ip` count.

**Step 3 — on the device: verify the CA and build the credential**

```sh
openssl x509 -in ca.crt -noout -fingerprint -sha256
./my-zerotier-linux enroll -server vpn.example.com:8443 \
  -key alice.key -cert alice.crt -ca ca.crt -out alice.json
```

Compare the CA fingerprint with the value the administrator told you. Only continue if it matches: the CA you trust here decides which controller your device will talk to.

| Flag | Meaning |
| --- | --- |
| `-server` | Controller `host:port`, exactly as given at `init` |
| `-key` | The local private key from step 1 |
| `-cert` | The approved certificate from step 2 |
| `-ca` | The independently verified CA certificate |
| `-out` | New credential file (mode `0600`, never overwritten) |

`enroll` checks that the certificate matches the private key and was signed by the given CA for both client and server use. Output:

```text
Created private credential alice.json. Keep it and alice.key confidential.
```

Both `alice.key` and `alice.json` contain the private key. After you have verified that `alice.json` works you may delete `alice.key`; but keep in mind that you need a **new** key for a later rotation anyway.

### 7.3 Allow traffic

A newly added device cannot exchange any traffic until you add rules (section 9). For two devices that should talk in both directions:

```sh
./my-zerotier allow -data controller-data -from alice -to bob
./my-zerotier allow -data controller-data -from bob -to alice
```

### 7.4 Verify the result

From any authorized device:

```sh
./my-zerotier-linux status -credential alice.json
```

```text
Peer alice (10.77.0.1), network 10.77.0.0/24, 2 authorized peers
Static default-deny policy: 2 directional allow rules
  alice  10.77.0.1
  bob  10.77.0.2
```

## 8. Running a device

### 8.1 Start the client

On each device, as root (or with `CAP_NET_ADMIN`), with its own credential:

```sh
sudo ./my-zerotier-linux run -credential alice.json
# on bob instead: -credential bob.json
```

`run` options:

| Flag | Default | Meaning |
| --- | --- | --- |
| `-credential` | (required) | The device's private credential file |
| `-interface` | `mzt0` | Name of the TUN interface to create (1 to 15 bytes) |

What happens:

1. The client loads the credential and requests the configuration from the controller. If the controller cannot be reached at this point, `run` exits with an error.
2. It finds its own entry by the fingerprint of its certificate. If its certificate is not in the list, it stops.
3. It creates the TUN interface, assigns the IPv4 address (and IPv6 address, if any) with the network's prefix length, sets the MTU to **1280** and brings the interface up. The log shows, for example: `interface mzt0 active for alice ([10.77.0.1/24])`.
4. For every other device with at least one allow rule in either direction, it opens a relayed session and an end-to-end TLS 1.3 session. The log shows `peer bob connected through relay`.
5. It re-reads the configuration every 2 seconds and recreates the interface whenever the configuration changes.

Test the connection:

```sh
# on alice
ping 10.77.0.2
# on bob
ping 10.77.0.1
```

The local firewall on each device must allow ICMP and any application ports you use on the `mzt0` interface.

### 8.2 Interface name

The interface is created fresh. If an interface with the same name already exists, `run` fails with `interface "mzt0" already exists`. To run two clients on one machine (for example in a lab), give each its own name:

```sh
sudo ./my-zerotier-linux run -credential alice.json -interface mzt1
```

The interface is not persistent: it disappears when the client stops.

### 8.3 Stopping

Press `Ctrl-C` or send `SIGTERM`. The client closes its sessions and removes the TUN interface.

### 8.4 Behaviour during problems

| Situation | Behaviour |
| --- | --- |
| A peer session breaks | The client reconnects with exponential backoff and random jitter, starting at about 1 to 2 seconds and growing up to 30 seconds; after 30 seconds of stable connection the backoff resets. |
| The controller cannot be reached for a refresh | The client **closes the tunnel** (logged once as `controller refresh failed; tunnel closed: ...`) and keeps trying every 2 seconds. When the controller answers again, it recreates the tunnel. A short controller outage therefore interrupts the overlay. |
| Configuration changed | Tunnel is recreated; existing sessions end. |
| Writing to the TUN device fails | The client exits with an error instead of only reconnecting the peer. |
| An outgoing packet is larger than 1280 bytes | It is dropped and logged (`tunnel packet exceeds MTU`). |
| An incoming frame is larger than 1280 bytes | That peer session is closed. |
| The send queue of a peer is full (128 packets) | Packets are dropped (`queue full for peer bob; packet dropped`). |
| A certificate in use expires | The session is closed at the earliest expiry time of the device, controller and CA certificates involved, and the client reconnects (which then fails until the certificate is renewed). |

### 8.5 Platforms

The client runs on Linux only (amd64, arm64 and other architectures Go supports). macOS can run the controller and all administrative commands, but not the tunnel.

### 8.6 Running as a service

No service units are shipped with this version. If you run the client under a service manager, configure it to restart the process after it exits, because `run` exits when the controller is unreachable at startup, when the device is no longer authorized and after a TUN write error. The process needs `CAP_NET_ADMIN`, access to `/dev/net/tun` and the `ip` command in `PATH`.

### 8.7 Status

```sh
./my-zerotier-linux status -credential alice.json
```

`status` fetches the configuration from the controller with the device's credential and prints the authorized network. It needs no root. It shows the **authorized member list, not the live connection state**; check the `run` log to see which peers are connected. `status` also accepts `-interface`, but that flag has no effect for `status`.

With IPv6 configured the output also contains a line like `IPv6 network fd77::/64, local address fd77::1`, and with the service filter enabled a line `Experimental service default-deny: N directional service rules`.

## 9. Access rules

### 9.1 How the rules work

- A rule is directional: `-from alice -to bob` permits packets whose source is alice's address and whose destination is bob's address.
- Without the service filter, a rule permits **all** IPv4 and IPv6 packets in that direction. It is not a stateful firewall: replies need the reverse rule.
- Rules apply to both address families.
- The sender filters outgoing packets and the receiver filters incoming packets independently, so a correctly working receiver protects itself even against a misbehaving sender.
- Every packet must carry the exact assigned source and destination address of the two devices. Packets to other destinations are not forwarded; a packet with a wrong source address from a peer ends that session (`invalid or spoofed packet from bob`).
- The relay pairs two devices only if at least one direction is allowed.

### 9.2 Allow and deny

```sh
# allow both directions between alice and bob
./my-zerotier allow -data controller-data -from alice -to bob
./my-zerotier allow -data controller-data -from bob -to alice

# remove one direction
./my-zerotier deny -data controller-data -from alice -to bob
```

Both commands print `Updated alice -> bob. Controller and updated clients reload asynchronously.`

| Flag | Default | Meaning |
| --- | --- | --- |
| `-data` | `controller-data` | Controller data directory |
| `-from` | (required) | Source device ID |
| `-to` | (required) | Destination device ID |

`allow` for an existing rule and `deny` for a missing rule change nothing. `deny` also removes all service rules for that direction.

### 9.3 Enabling default deny on a legacy network

Only for networks whose state has no policy (created before default deny was introduced):

```sh
./my-zerotier policy-enable -data controller-data
```

Output: `Default-deny enabled with no allow rules. Controller and updated clients reload asynchronously.` From that moment all traffic is blocked until you add `allow` rules. Networks created with `init` at this tag already have a policy, and the command reports `default-deny policy already enabled`.

### 9.4 Experimental service rules

Service rules restrict an allowed direction further, to specific protocols and destination ports. They are experimental.

Important properties:

- Enabling them is **default deny for all directions**: right after `service-enable` all traffic is dropped until you add service rules.
- Each service rule requires the matching device rule (`allow`) to exist.
- `tcp` and `udp` match an exact **destination** port (1 to 65535). `icmp` (IPv4) and `icmp6` (IPv6) allow all ICMP types and take no port.
- At most 4,096 service rules.
- There is no automatic return traffic. TCP and UDP replies go to changing client ports and would need explicit reverse rules, so in practice service rules suit ICMP and one-way UDP better than interactive TCP.
- Other protocols, IPv4 fragments and IPv4 options, and IPv6 extension headers (including fragments) are dropped while the service filter is on.
- ICMP error messages are not tied to connections.
- Operating system firewalls remain necessary.

Before enabling the service filter, update the controller **and all clients** to this binary: older strict decoders reject the additional JSON field.

**Step by step**

```sh
./my-zerotier service-enable -data controller-data
./my-zerotier service-allow -data controller-data -from alice -to bob -protocol udp -port 53
./my-zerotier service-allow -data controller-data -from alice -to bob -protocol icmp
./my-zerotier service-allow -data controller-data -from bob -to alice -protocol icmp
./my-zerotier service-allow -data controller-data -from alice -to bob -protocol icmp6
./my-zerotier service-allow -data controller-data -from bob -to alice -protocol icmp6
```

`service-deny` with the same flags removes a rule:

```sh
./my-zerotier service-deny -data controller-data -from alice -to bob -protocol udp -port 53
```

| Flag | Default | Meaning |
| --- | --- | --- |
| `-data` | `controller-data` | Controller data directory |
| `-from` | (required) | Source device ID |
| `-to` | (required) | Destination device ID |
| `-protocol` | (required) | `tcp`, `udp`, `icmp` or `icmp6` |
| `-port` | `0` | Destination port for `tcp` and `udp`; omit for `icmp` and `icmp6` |

**All at once with `service-apply`**

`service-apply` replaces the complete service rule set in one atomic write and enables the filter if it was off. Example `services.json`:

```json
{"allowed":[
  {"from":"alice","to":"bob","protocol":"icmp"},
  {"from":"bob","to":"alice","protocol":"icmp"},
  {"from":"alice","to":"bob","protocol":"udp","port":53}
]}
```

```sh
./my-zerotier service-apply -data controller-data -rules services.json
```

Output: `Applied 3 service rules atomically on disk; controller and current clients reload asynchronously.`

The file contains only the required `allowed` array. `{"allowed":[]}` blocks all services. Invalid, duplicate or uncovered rules (without a matching `allow`) are rejected before anything is written. The atomic replacement applies to the file only; clients still pick up the change asynchronously.

There is deliberately no command to switch the service filter off again. To return to device-level rules only you would have to edit the state by hand, which is not supported.

### 9.5 IPv6 setup

IPv6 is optional and runs over the same sessions and rules as IPv4. IPv4 is always required.

1. Update the controller and **all clients** first: older binaries with the strict JSON decoder reject the new fields.
2. Configure the IPv6 network. It must be a canonical `/64` inside `fd00::/8` (a unique local address range) that does not collide with other networks:

   ```sh
   ./my-zerotier ipv6-network -data controller-data -network fd77::/64
   ```

3. Assign addresses. Each must be inside the `/64`, unique, and not the prefix address itself (`fd77::`):

   ```sh
   ./my-zerotier ipv6-assign -data controller-data -id alice -ip fd77::1
   ./my-zerotier ipv6-assign -data controller-data -id bob -ip fd77::2
   ```

4. After the asynchronous reload, test on alice:

   ```sh
   ping -6 fd77::2
   ```

A device without an IPv6 assignment stays IPv4-only. To remove IPv6:

```sh
./my-zerotier ipv6-assign -data controller-data -id alice -ip none
./my-zerotier ipv6-assign -data controller-data -id bob -ip none
./my-zerotier ipv6-network -data controller-data -network none
```

Remove all assignments first; changing or removing the prefix is rejected while assignments do not fit the new setting. Multicast, neighbour discovery across the overlay, jumbograms and routing of other prefixes are not supported.

## 10. Day-to-day operation

### 10.1 How changes take effect

Every changing command (`add-peer`, `approve`, `rotate-peer`, `remove-peer`, `policy-enable`, `allow`, `deny`, `service-*`, `ipv6-network`, `ipv6-assign`, `renew-server`):

1. takes an exclusive advisory lock on `controller-data/.state.lock` (a second concurrent command fails with `controller state is locked by another writer` and must be repeated),
2. loads and validates the state,
3. writes a new `state.json` atomically (temporary file, `fsync`, rename, directory `fsync`).

The running controller notices the change within about a second and drops all relay sessions; clients notice within about 2 seconds and recreate their tunnels. The CLI does **not** confirm that this has happened.

The lock protects only against other commands of this binary. Manual edits, older binaries and file systems without reliable `flock` bypass it.

If a sync step fails after the write, the CLI reports that durability is uncertain. In that case, check the state and output files before retrying.

To check whether the controller has loaded the file, use `check-config` (section 11.1).

### 10.2 Changing rules

Add or remove rules at any time with `allow`, `deny` and the service commands. Expect a short interruption: a configuration change ends all relay sessions and every client rebuilds its tunnel.

### 10.3 Removing a device (revocation)

```sh
./my-zerotier remove-peer -data controller-data -id bob
```

Output: `Peer removed from disk. Controller and updated clients reload asynchronously; CLI does not confirm enforcement.`

`remove-peer` removes the device, all rules and service rules that mention it, and records its public key in the key history so the same key can never be approved again.

What revocation means in this version:

- Once the controller has reloaded (about one second), it no longer accepts bob's certificate and drops all sessions; bob's next configuration request fails.
- Up-to-date clients drop their sessions to bob after their next refresh.
- There is **no guaranteed revocation deadline** and no signed short-lived lease. A compromised controller or a manipulated client can ignore the change.
- `remove-peer` also works when the controller's server certificate has already expired (as long as the CA is valid), so you can revoke offline. The controller will still stay closed until the certificate is renewed and the controller restarted.

If bob's credential was stolen, removing bob is the only countermeasure; there is no certificate revocation list.

### 10.4 Rotating a device key

Use this when a device key may be exposed, when its certificate approaches its one-year expiry, or routinely. The device creates a **new** key; addresses and rules are kept.

1. On the device:

   ```sh
   ./my-zerotier-linux keygen -id alice -key alice-new.key -request alice-new.csr
   shasum -a 256 alice-new.csr
   ```

2. On the controller, after checking identity and fingerprint:

   ```sh
   ./my-zerotier rotate-peer -data controller-data -id alice \
     -request alice-new.csr -out alice-new.crt
   ```

   `rotate-peer` uses the same flags as `approve` except `-ip`: the existing address is kept, and passing `-ip` is rejected with `rotate-peer preserves the existing address; do not specify -ip`.

3. Send `alice-new.crt` (and `ca.crt`, if the device does not have it) back. On the device, after verifying the CA fingerprint:

   ```sh
   ./my-zerotier-linux enroll -server vpn.example.com:8443 \
     -key alice-new.key -cert alice-new.crt -ca ca.crt -out alice-new.json
   ```

4. Stop the old client and start it with the new credential:

   ```sh
   sudo ./my-zerotier-linux run -credential alice-new.json
   ```

Once the controller has reloaded, the old certificate is no longer accepted and active sessions end. There is no seamless rotation: the device is offline between the reload and the restart with the new credential.

This also works for devices that were added with `add-peer`: they simply create their first own key with `keygen`.

**Key history.** The controller remembers the SHA-256 fingerprints of all public keys it has authorized (up to 32,768 entries) and refuses to authorize them again, also after rotation or removal (`peer public key was previously authorized`). An old backup, a manual edit or loss of the history can undo this protection. Requests themselves have no expiry and are not single-use before their first approval, so always verify that a request is fresh and authentic.

### 10.5 Renewing device certificates

Device certificates expire after one year at most. There is no automatic or online renewal in this version. Renew a device by rotating its key (section 10.4) before the certificate expires. An expired certificate ends the device's sessions and prevents new connections.

### 10.6 Renewing the controller certificate

The controller's server certificate is valid for one year. Renew it on the controller host:

```sh
./my-zerotier renew-server -data controller-data
```

Output: `Controller certificate and key renewed on disk; restart the controller to restore service.`

Then restart `serve`. A running controller detects the changed identity (`controller TLS identity changed; restart required`), closes its relay and stays closed until restarted.

- A new server key is generated; the new certificate is valid for at most one year and not longer than the CA.
- The CA key and all device certificates stay the same, so no new credentials are needed as long as CA and address are unchanged.
- An already expired server certificate can be renewed. An expired CA cannot.

### 10.7 Moving the controller

There is no command to change the controller address. If the new host is reachable under the **same** name and port (for example by moving the DNS record), you can move the controller:

1. Stop `serve` on the old host.
2. Copy `controller-data` to the new host over a secure channel, keeping mode `0700` on the directory and `0600` on `state.json`.
3. Start `serve` on the new host and update DNS.

If the name changes, you need a new `init` and new credentials for every device: the name is part of the server certificate and of every credential (`server` field).

### 10.8 Backup and restore

**Backup.** Everything is in `controller-data/state.json`. Back it up encrypted, for example after every change:

```sh
tar -C . -czf - controller-data/state.json | \
  openssl enc -aes-256-cbc -pbkdf2 -salt -out controller-state-$(date +%F).tar.gz.enc
```

(Any tool that produces an encrypted archive is fine; the point is that the file contains the CA private key.) There is no built-in backup.

**Restore.** Stop `serve`, restore `state.json` into the data directory with mode `0600` (directory `0700`) and start `serve` again.

Be aware of what a restore does:

- it brings back the devices and rules of that moment, so devices removed since then become authorized again,
- it brings back an older key history, so keys rotated since then can be approved again,
- there is no rollback protection.

Losing the CA key means a full new setup and new credentials for all devices.

### 10.9 Upgrades

All JSON files are read strictly: unknown fields, duplicate fields, trailing data and documents larger than 4 MiB are rejected. When a newer binary adds fields to `state.json` or to the configuration the controller sends, older binaries can no longer read them. Upgrade in this order:

1. the controller binary and the binary you use for administrative commands,
2. all clients,
3. only then use features that add new fields (the key history is written after the first key change, IPv6 and service rules add new fields).

Clients that are older than the controller's policy feature do not send the configuration revision and are rejected by the relay once a policy exists.

## 11. Further features of this version

### 11.1 Verifying the loaded configuration: `check-config`

`check-config` compares the configuration in `state.json` with the configuration the running controller actually serves. It needs the credential of a device that is still authorized. A practical approach is a dedicated administrative device entry with no rules, used only on the controller host:

```sh
./my-zerotier add-peer -data controller-data \
  -id admin -ip 10.77.0.250 -out credentials/admin.json
./my-zerotier check-config -data controller-data -credential credentials/admin.json
```

(The `admin` entry counts toward the limit of 32 devices; without rules it cannot exchange traffic with anyone.)

Output on success:

```text
On-disk configuration: <hash>
Controller configuration: <hash>
Controller configuration matches the local snapshot; client convergence is not verified.
```

If the hashes differ, the command fails with `controller has not loaded the on-disk configuration`; wait a second and try again. A match does not prove that every client has updated, nor that tampered devices enforce the rules.

### 11.2 Logs

There are no metrics in this version; the log is the only operational signal. Controller and client write plain text log lines to standard error; the controller prints its start-up line to standard output. Useful messages:

| Message | Where | Meaning |
| --- | --- | --- |
| `Controller listening on ...` | Controller | Started successfully |
| `controller configuration unavailable; relay closed: ...` | Controller | `state.json` is invalid or unreadable; failing closed |
| `controller configuration restored` | Controller | State is valid again |
| `interface mzt0 active for alice (...)` | Client | Tunnel created with these addresses |
| `peer bob connected through relay` | Client | Session to bob established |
| `peer bob disconnected: ...` | Client | Session ended; will reconnect |
| `controller refresh failed; tunnel closed: ...` | Client | Controller unreachable; tunnel down until it answers |

### 11.3 Built-in limits and timeouts

| Limit | Value |
| --- | --- |
| Devices per network | 32 |
| Simultaneous TCP connections at the controller | 1,152 (further connections wait in the OS backlog) |
| Relay endpoints (waiting or active) | 1,024 in total, 32 per device, 1 per directed device pair |
| Waiting relay endpoint without partner | closed after 30 seconds |
| HTTP request header read timeout | 10 seconds |
| Request and response header size | 16 KiB |
| Client connect and configuration timeout | 10 seconds; relay handshake 40 seconds |
| Tunnel MTU | 1280 bytes |
| Per-peer send queue | 128 packets |
| Service rules | 4,096 |
| JSON documents | 4 MiB |
| Enrollment files (request, key, certificate) | 64 KiB each |
| Key history | 32,768 entries |

None of these limits is configurable.

### 11.4 Not available in this version

The following features are not part of `v0.1-copilot`:

- release binaries, checksums and release notes,
- service units or packages for controller or clients,
- macOS or other non-Linux clients,
- direct connections between devices, UDP transport or NAT traversal,
- a standby or high-availability controller,
- signed configuration and signed short-lived authorization leases,
- enrollment tokens or an online join flow,
- online or automatic certificate renewal,
- CA rotation and changing the controller address,
- metrics, structured logging and a version command,
- Ethernet bridging, multicast, subnet routing and exit nodes.

## 12. Troubleshooting

Command-line errors are printed with the prefix `Fehler:` (German for "error") followed by the actual message, for example `Fehler: -server is required`. The messages themselves are in English.

### Setup and administration

| Message | Meaning | What to do |
| --- | --- | --- |
| `-server is required` (and similar `... are required`) | A mandatory flag is missing | Add the flag; see `<command> -h` |
| `server must be a host:port address` | `-server` has no port or host | Use `vpn.example.com:8443` |
| `create new data directory: ...: file exists` | `init` refuses to reuse a directory | Choose a new path; never run `init` over a live state |
| `network must be a canonical IPv4 prefix no smaller than /30` | Wrong `-network` | Use a prefix with zero host bits, for example `10.77.0.0/24` |
| `controller state is locked by another writer: ...` | Another command is changing the state | Wait and run the command again |
| `open credentials/alice.json: file exists` | Output files are never overwritten | Choose a new name or remove the old file deliberately |
| `invalid ID "..."` | ID does not match the allowed pattern | Use 1 to 32 characters: letters, digits, `_`, `-`, starting with a letter or digit |
| `peer alice already exists` | ID taken | Pick another ID or remove the old entry |
| `invalid peer "..." or IP "..."` | IP outside the network or invalid | Use an address inside `10.77.0.0/24` |
| `peer bob uses a network or broadcast address` | `.0` or `.255` in a `/24` | Use a host address |
| `duplicate peer ID, IP, certificate or public key: ...` | Conflict with an existing device | Use a unique IP and a new key |
| `at most 32 peers are supported in the experimental full-mesh implementation` | Device limit reached | Remove unused devices |
| `request ID does not match approved ID` | `-id` differs from the ID in the request | Approve with the ID used at `keygen`, or have the device create a new request |
| `only Ed25519 enrollment keys are supported` | Request not made by `keygen` | Create the request with `keygen` |
| `peer public key was previously authorized` | The key was used before (key history) | Create a new key with `keygen` |
| `legacy configuration: enable default-deny policy first` | `allow`/`deny` on a network without policy | Run `policy-enable`, then add rules |
| `invalid destination peer "..."` | Unknown `-to`, or `-from` equals `-to` | Check IDs with `status` |
| `service policy is not enabled` | `service-allow` before `service-enable` | Run `service-enable` or `service-apply` |
| `service requires an existing directional allow and a valid protocol and port` | Missing `allow` rule, or port given for ICMP / missing for TCP/UDP | Add the `allow` rule; fix `-protocol`/`-port` |
| `IPv6 network must be a canonical fd00::/8 ULA /64 prefix` | Wrong `-network` for IPv6 | Use for example `fd77::/64` |
| `invalid IPv6 address "..." for peer alice` | Address outside the `/64`, the prefix address itself, or no IPv6 network set | Configure `ipv6-network` first and pick an address inside it |
| `invalid controller PKI: server certificate verification: ...` | Server certificate expired or does not match the host | Run `renew-server`, then restart `serve` |
| `CA expires too soon to issue a peer certificate` | The CA is about to expire | A new setup is needed; there is no CA rotation |

### Controller

| Message | Meaning | What to do |
| --- | --- | --- |
| `WARNING: legacy network allows all peer traffic; ...` | Network has no policy | Run `policy-enable` and add rules |
| `controller configuration unavailable; relay closed: ...` | `state.json` invalid, unreadable or inconsistent | Fix or restore the file; the controller recovers on its own (`controller configuration restored`) |
| `controller TLS identity changed; restart required` | CA or server certificate in `state.json` changed (for example after `renew-server`) | Restart `serve` |
| `listen tcp :8443: bind: address already in use` | Port in use | Stop the other process or choose another `-listen` |

### Client

| Message | Meaning | What to do |
| --- | --- | --- |
| `TUN client is currently supported only on Linux` | `run` on a non-Linux system | Use a Linux device |
| `open tunnel: permission denied` or `open tunnel: create TUN: operation not permitted` | Missing privileges | Run as root or with `CAP_NET_ADMIN` |
| `open tunnel: interface "mzt0" already exists` | Another client or a leftover interface | Stop the other client or use `-interface mzt1` |
| `open tunnel: interface name must be 1-15 bytes` | `-interface` too long | Use a shorter name |
| `open tunnel: ip [...]: exec: "ip": executable file not found in $PATH` | `ip` command missing | Install iproute2 or BusyBox `ip` |
| `controller: 403 Forbidden` | The controller does not know this certificate (device removed or rotated) | Check with the administrator; enroll again if needed |
| `controller: 503 Service Unavailable` | Controller is failing closed | The administrator must fix `state.json` or restart after `renew-server` |
| `... x509: certificate signed by unknown authority` or `... certificate is valid for ..., not ...` | Wrong CA in the credential, or controller address does not match the certificate | Check the `server` and `ca` values in the credential |
| `... connection refused` / `i/o timeout` | Controller not reachable | Check DNS, firewall, `serve` status |
| `own certificate is not authorized` | Configuration does not contain the device | The device was removed; contact the administrator |
| `peer bob: relay: 403 Forbidden` | No allow rule in either direction for the pair | Add `allow` rules |
| `peer bob: relay: 409 Conflict` | Outdated configuration revision, or a session for this pair is already waiting | Usually resolves on the next refresh; otherwise check that all binaries are current |
| `peer bob: relay: 429 Too Many Requests` | Relay connection limit reached | Reduce load; limits are fixed |
| `peer bob: peer TLS: ...` | End-to-end TLS failed, for example `peer certificate does not match authorized peer bob` | The two devices see different configurations or one uses an outdated credential; wait for refresh, then check rotation |
| `peer bob disconnected: invalid or spoofed packet from bob` | bob sent a packet with a wrong address | Investigate bob |
| `certificate has expired` | A device, controller or CA certificate has expired | Renew (sections 10.5, 10.6) |
| `tunnel stopped: ... write tunnel: ...` | Writing to the TUN device failed | Check the system; restart the client |

### Ping does not work although everything is connected

1. Check both rules exist (`status` shows the number of rules).
2. Check the device firewalls allow ICMP on `mzt0`.
3. Check that `10.77.0.0/24` does not overlap a local network or VPN route (`ip route`).
4. If the service filter is on, check that `icmp` (and `icmp6`) service rules exist in both directions.
5. Use `check-config` to confirm the controller has loaded your latest change.

## 13. Security notes and known limits

This is the prototype baseline. It was developed autonomously and had **not been reviewed** at the time of tagging. The findings of the first review of exactly this state are collected in [`docs/review-v0.1-copilot.md`](../../review-v0.1-copilot.md) on the `main` branch. Read it before you rely on any property described here.

### What the design protects

- All connections use TLS 1.3 from the Go standard library; there is no custom cryptography.
- Device-to-device traffic is protected by a second, end-to-end TLS 1.3 session. A relay that only forwards bytes, and whose controller and CA are not compromised, cannot read the content. Each side pins the exact certificate from the controller's member list and also checks the CA chain and key usage.
- Traffic is denied by default and checked per direction at sender and receiver.
- Source and destination addresses are checked against the assigned addresses (anti-spoofing).
- All inputs have size limits and all connection phases have timeouts.
- An invalid state makes the controller fail closed.

### What it does not protect

- **The controller is a full trust anchor.** It holds the CA key and the member list. A compromised controller can add devices, replace certificates and intercept connections. The configuration is not separately signed.
- With `add-peer`, the controller also sees the device's private key. Prefer offline enrollment.
- A certificate request proves possession of a key, not identity. Fingerprints must be compared over an independent channel.
- There is **no guaranteed revocation deadline**, no signed short-lived lease and no protected time source. The certificate-expiry deadline on sessions is a local mechanism; wrong clocks, time jumps, suspend or tampered clients defeat it, and the relay does not enforce it.
- A tampered client can ignore the rules on its side. Correct receivers still check independently. The configuration revision is not proof of unmodified client software.
- No rollback protection: restoring an old backup can re-authorize removed devices and old keys.
- The relay sees metadata: which devices talk, when, and how much.
- The service filter is stateless and experimental; it is not a firewall replacement. Keep operating-system firewalls.

### Operational limits

- The relay is a single point of failure. There is no high availability.
- TCP over TCP can add latency and head-of-line blocking under loss or congestion.
- The full mesh grows quadratically; the network is limited to 32 devices.
- A short controller outage closes all client tunnels until the controller is back.
- Connection limits are not a complete protection against resource abuse; there are no bandwidth quotas and no per-client rate limits for TLS handshakes or requests. An attacker can exhaust the global connection limit. A waiting relay endpoint whose client disconnected can occupy a slot for up to 30 seconds.
- Certificates: devices and server at most one year, CA ten years; renewal is manual, CA rotation is missing, and changing the controller host name requires a new setup.
- Only unicast between assigned addresses; IPv6 limited to one ULA `/64`; no multicast, neighbour discovery, jumbograms, subnet routing or exit nodes.
- Fixed MTU of 1280 bytes, no path MTU discovery.
- No automatic backup, no packaging, no service management, no hardened privilege separation.
- State and credential files are not checked for safe permissions when loaded at this tag; protect them yourself.
